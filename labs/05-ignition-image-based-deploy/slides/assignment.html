Check the remotes and set the default: git remote -v: origin must show your username; then gh repo set-default <you>/cicd-for-ignition so gh targets your fork, not the course repo. Only the stretch needs this (its PRs); it's once per clone and probably done in an earlier lab. Then code . to open VS Code.
5
scripts/setup.sh brings up the stack: the local authoring gateway (:8088, bind-mounted), test (:8089) and production (:8090), both empty until their first image deploy, plus TimescaleDB. Four containers, no runner: today you are the last mile of the pipeline.

We do · together
WE DO · 1
Build the image, stamp it with its commit, prove the cache
Build the gateway image with a real provenance stamp, then prove the layer cache behaves like the teaching slide said.
1
scripts/build-image.sh builds and tags :sha-<short> + :local. It passes --build-arg GIT_SHA=$(git rev-parse --short HEAD) for you. docker history shows the baked layers, newest on top. Which layer is the biggest?
2
Read the revision label back and confirm it matches the last commit. That's how you trace any container to its commit.
3
A trap first: touch a project file and rebuild. Every layer stays CACHED: Docker checksums the content of each COPY's inputs, and timestamps are invisible to it. Then append a newline to the same file and rebuild: only the projects/ layer rebuilds, and the tag now ends in -dirty.
4
Drop a dummy file into third-party-modules/ and rebuild. That COPY sits higher in the Dockerfile: the 5-second module check, modules, config and projects all rebuild.
5
Clean up and rebuild. Delete the dummy, undo the newline, rebuild: the tag must read sha-<short> without -dirty, or both edits ship in every later build.
# 1: build, then read the layers
scripts/build-image.sh
docker history cicd-lab-05-ignition:local

# 2: trace the image to its commit
docker inspect -f '{{ index .Config.Labels
  "org.opencontainers.image.revision" }}' \
  cicd-lab-05-ignition:local
git rev-parse --short HEAD

# 3: a timestamp busts nothing, content does
touch projects/example-project/project.json
scripts/build-image.sh
printf '\n' >> projects/example-project/project.json
scripts/build-image.sh

# 4: a new file higher up busts much more
echo test > third-party-modules/dummy.txt
scripts/build-image.sh

# 5: clean up, then rebuild from the commit
rm third-party-modules/dummy.txt && git checkout -- projects/
scripts/build-image.sh
Layer order

A busted layer busts everything after it: that's why daily project edits rebuild in seconds.

WE DO · 2
Run the image with nothing mounted, and read what got baked
The self-contained proof: the project shows up because it's inside the image, with no ./projects mount and no scan call.
1
Run the image on a spare port with no bind mounts, detached (-d). build-image.sh printed this exact command. The last argument tells the gateway where the baked third-party modules live; leave it out and the log says Error adding historian.
2
Follow the boot with docker logs -f demo. Once it prints "Starting project: example-project", open http://localhost:9088 → example-project is there. Ctrl-C only leaves the logs.
3
Meanwhile: what did .dockerignore keep out? Your first build's transferring context line said about 5 MB; du -sh . says about 11 MB. The gateway's .resources/ blob stores and the lab material never reached Docker. For the exact list, the probe image from lab.md shows only projects/, services/ and third-party-modules/.
4
Read the image, not the repo. In Docker Desktop (Images → cicd-lab-05-ignition → Files) or with --entrypoint find, find all four COPYed artifacts: projects/, config/ and modules.json under /usr/local/bin/ignition/data/, and /third-party-modules. Not there: README.md, docs/, .env, and the OPC UA module's opcua-module login: the Dockerfile's sed step makes every gateway create its own at first boot.
# 1: the self-contained proof (-d = detached)
docker run -d --rm --name demo -p 9088:8088 \
  -e ACCEPT_IGNITION_EULA=Y -e IGNITION_EDITION=standard \
  -e GATEWAY_ADMIN_USERNAME=admin \
  -e GATEWAY_ADMIN_PASSWORD=password \
  cicd-lab-05-ignition:local \
  -n demo -- -Dignition.allowunsignedmodules=true \
  -Dignition.gateway.externalModulesFolder=/third-party-modules

# 2: follow the boot (Ctrl-C leaves the logs)
docker logs -f demo

# 3: on disk vs what reached Docker
du -sh . projects/.resources \
  services/config/resources/.resources slides docs scripts

# 4: read the image itself
docker run --rm --entrypoint find cicd-lab-05-ignition:local \
  /usr/local/bin/ignition/data/projects -maxdepth 2

# done exploring? stop it (--rm removes it)
docker stop demo

Part 1.1
PART 1.1
Bake a config change into the image and read it back
Gateway config is a layer like any other. Change one value, rebuild, and prove the new value is in the image, not just in your folder.
1
Open services/config/resources/core/ignition/system-properties/config.json and replace the text of "homepageNotes" with a note of your own. A logged-in user sees it on the gateway's Home page.
2
Rebuild. Which layers rebuilt, and which stayed CACHED? Why did the projects/ layer rebuild although you never touched a project?
3
Prove it from the image: swap the entrypoint for grep and read the baked file.
# 1: edit the note
"homepageNotes": "Baked into the gateway image.",

# 2: rebuild (the tag says -dirty for now)
scripts/build-image.sh

# 3: read it back from the image
docker run --rm --entrypoint grep \
  cicd-lab-05-ignition:local homepageNotes \
  /usr/local/bin/ignition/data/config/resources/core/ignition/system-properties/config.json
Why it matters

In Part 2 you deploy this image and see the note on the test gateway's Home page: config you never typed into that gateway, delivered by replacing the container.

Part 1.2
PART 1.2
Keep a stray gateway backup out of the image with .dockerignore
COPY projects/ copies everything in that folder. Someone leaves a gateway backup there: a .gwbk holds the internal database, user passwords included.
1
Simulate the stray file, rebuild, and find it in the image. It's there.
2
Add **/*.gwbk to .dockerignore, with a one-line comment that says why. Rebuild and run the same find: gone from the image, still on your disk.
3
Delete the stray file. git status must show only your two edits. Commit them and merge the branch into your local main: that merge stands in for merging a PR on GitHub, so don't push this main.
4
Rebuild. The tag reads sha-<short> without -dirty: that clean image is what you deploy in Part 2.
# 1: a stray backup in projects/
echo "pretend 1 GB backup" > projects/old-backup.gwbk
scripts/build-image.sh
docker run --rm --entrypoint find cicd-lab-05-ignition:local \
  /usr/local/bin/ignition/data/projects -maxdepth 1

# 2: in .dockerignore, then rebuild + find again
# Gateway backups hold the internal DB: never bake one
**/*.gwbk

# 3: clean up, commit, merge locally (no push)
rm projects/old-backup.gwbk
git add .dockerignore services/config/resources/core/ignition/system-properties/config.json
git commit -m "Bake a homepage note, keep backups out"
git checkout main && git merge feature/bake-a-change

# 4: the clean build Part 2 deploys
scripts/build-image.sh
Done when

Your note is in the image (proven with --entrypoint), *.gwbk is not (proven with find before and after), and your latest tag has no -dirty.

Part 2 · read first
2 · READ FIRST
Why we deploy locally today, and what GitHub Actions would do instead
Nothing to type on this slide: it only explains the plan. In a real setup this part is automated by the same Actions you built in Lab 04; today you type the workflow's commands yourself, starting on the next slide (Part 2.1).
  • Same triggers as Lab 04. A merge to main would fire lab05-deploy.yml, a tag would fire lab05-release.yml. Only the steps inside the jobs change: build + push + pull + recreate, instead of copy + scan.
  • Why not do that now? The gateway image is ~2 GB. Between GitHub's datacenter and a registry that upload is seconds; from ten course laptops, it's your whole hour. The transport isn't the lesson.
  • So today, you are the pipeline. Every command in Parts 2.1 to 2.3 is a line the workflow would run. Type them once by hand and the automation never feels like magic again.
# FOR REFERENCE ONLY, do NOT run this. It's what
# a CI deploy job would run, pulling from a registry:
#
#   docker pull ghcr.io/<you>/<repo>:sha-<short>
#   IGNITION_TEST_IMAGE=ghcr.io/<you>/<repo>:sha-<short> \
#     docker compose up -d ignition-test

# YOUR deploy, in Part 2.1 (next slide): local
# image, no registry, so no pull:
IGNITION_TEST_IMAGE=cicd-lab-05-ignition:sha-<short> \
  docker compose up -d ignition-test
Same deploy

Your version drops only the docker pull line: your image store already holds the build. Everything else is identical to what the workflow runs. Want to run the real thing, registry included? That's the stretch slide at the end, not now.

Part 2.1
PART 2.1
Deploy your image to the test gateway, command by command
No script today: you type the deploy yourself so you see there's nothing to it. No docker cp, no scan call: the container is replaced.
1
Find your clean tag (docker images, or the end of your last build's output) and write the :sha-<short> down: it is your rollback point in Part 2.3.
2
Before: ask test which commit it runs. A long hash that is none of your commits: the base image, an empty gateway. And the historian's database: Did not find any relations. The tables appear after the first deploy and survive every later one.
3
Deploy, one command: the immutable tag, never the moving :local. Then poll /StatusPing until RUNNING (a fresh-image boot re-commissions, so give it a few minutes).
4
Verify: the revision label now shows your sha. Launch example-project from :8089/app/home/perspective/session-launcher, and log in at :8089: the Home page shows your Part 1.1 note.
5
Run the psql line again: the historian's tables are there now, in TimescaleDB, not in the container.
# 2: before: which commit? and the DB
docker inspect -f '{{ index .Config.Labels
  "org.opencontainers.image.revision" }}' lab05-ignition-test
docker exec lab05-timescaledb \
  psql -U ignition -d ignition_test -c '\dt'

# 3: THE deploy, then wait for RUNNING
IGNITION_TEST_IMAGE=cicd-lab-05-ignition:sha-<short> \
  docker compose up -d ignition-test
curl -s localhost:8089/StatusPing   # repeat

# 4 + 5: run the inspect and psql lines again
Under the hood

docker-compose.yaml interpolates IGNITION_TEST_IMAGE into the test service's image:, with the base image as default. New image → compose recreates the container. A later bare docker compose up -d without the variable puts test back on the base image.

Part 2.2
PART 2.2
Ship a change end-to-end: edit, commit, rebuild, redeploy
The full loop, exactly what a pipeline would automate. Commit before you build, so each build gets its own immutable :sha tag.
1
Edit a Perspective view under projects/example-project/com.inductiveautomation.perspective/views/: make it visibly different (a title text in pages/overview/view.json works well).
2
Commit the change on a feature branch and merge it into your local main. As in Part 1, the merge stands in for the PR merge on GitHub: don't push this main. The commit is what gives the next build a new :sha tag.
3
Rebuild, then redeploy with the same one-liner from Part 2.1 and the new tag build-image.sh printed.
4
Verify at :8089: your view change is live and the revision label shows the new sha. docker images now shows two clean :sha-… tags: two deployable versions, both still on your machine.
# 2: commit so the next build gets a new sha
git checkout -b feature/tweak-view
# edit the view.json, then:
git status          # only your view should show up
git add projects/ && git commit -m "Change overview title"
git checkout main && git merge feature/tweak-view

# 3: rebuild + redeploy the new tag
scripts/build-image.sh
IGNITION_TEST_IMAGE=cicd-lab-05-ignition:sha-<new-short> \
  docker compose up -d ignition-test
This is the pipeline

Steps 1-4 are exactly what a deploy workflow automates on merge: build → tag → run. You're doing the pipeline's job by hand once, so the automation never feels like magic.

Part 2.3
PART 2.3
Roll back by running the previous build's tag
The image-based rollback: point the container at yesterday's name. No git surgery, no re-copying files, nothing rebuilt.
1
Pretend Part 2.2's change broke something on test. You need the previous version back, now.
2
Deploy the old :sha-<short> tag you wrote down in Part 2.1: the same one-liner, older name. The old image never went away; it's a name in your image store.
3
Verify at :8089: the view is back to its previous state, and the revision label shows the old sha.
4
Count the irreversible steps you just took. (It's zero: both versions still exist, and you can flip between them all afternoon.)
# 2: rollback = the same deploy, older tag
IGNITION_TEST_IMAGE=cicd-lab-05-ignition:sha-<old-sha> \
  docker compose up -d ignition-test

# 3: confirm which build test runs now
docker inspect -f '{{ index .Config.Labels
  "org.opencontainers.image.revision" }}' lab05-ignition-test
Compare

File-based rollback (Lab 04) meant re-running the pipeline on an older tag: it works, but it re-copies and re-scans. Here the previous version already exists as an artifact: rollback is just running it. That difference is the whole reason teams keep versioned images around.

Stretch · optional
STRETCH
Let GitHub build the image, then deploy it by hand
This moves the build half to CI: merge to main builds and pushes, a lab05-v* tag promotes. The deploy half stays yours. Needs your fork; a good take-home if the venue Wi-Fi hates 2 GB pulls.
0
Two prerequisites. Actions enabled on your fork (its Actions tab lists the workflows). And Docker logged in to GHCR with a token that has read:packages: the package is private by default, so the pull in step 2 says denied without it. (Or make the package public in its settings.)
1
Trigger lab05-deploy.yml: branch from GitHub's main (your local one holds unpushed merges), open a PR with a small project change and merge it on GitHub. Wait until the deploy run is green: there is no image to pull before.
2
Deploy it yourself: the run's summary page prints the image name. Pull it and point test at it: the same command as part 2, longer name.
3
Release: tag GitHub's main and push the tag. lab05-release.yml checks that :test was built from that commit, then re-tags it to :v0.1.0 + :production: no rebuild. Deploy it to :8090 with IGNITION_PRODUCTION_IMAGE.
4
The payoff: {{.Image}} is identical on test and production: production runs the exact bytes test validated. And you typed an image name twice: that last mile is what Labs 06 and 07 automate.
# 0: once: let Docker read your GHCR packages
gh auth refresh -h github.com -s read:packages
gh auth token | docker login ghcr.io -u <you> --password-stdin

# 1: branch from GitHub's main, PR, merge on GitHub
git fetch origin && git checkout -b feature/ci-build origin/main

# 2: copy the tag from the run summary, deploy it
docker pull ghcr.io/<you>/cicd-lab-05-ignition:sha-<short>
IGNITION_TEST_IMAGE=ghcr.io/<you>/cicd-lab-05-ignition:sha-<short> \
  docker compose up -d ignition-test

# 3: release (checked + promoted, no rebuild), deploy to :8090
git fetch origin
git tag lab05-v0.1.0 origin/main && git push origin lab05-v0.1.0
IGNITION_PRODUCTION_IMAGE=ghcr.io/<you>/cicd-lab-05-ignition:v0.1.0 \
  docker compose up -d ignition-production

# 4: the digest-equality proof
docker inspect -f '{{.Image}}' lab05-ignition-test
docker inspect -f '{{.Image}}' lab05-ignition-production
Build-once, promote-many

The release never rebuilds: it re-tags the image test validated, so production runs those exact bytes.
