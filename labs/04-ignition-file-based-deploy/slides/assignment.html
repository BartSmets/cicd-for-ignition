Before you start · setup
SETUP
First: your course fork, Actions on, this lab's folder
Part 2's deploy pipeline runs in your own fork's GitHub Actions, driving a self-hosted runner on your machine. So everyone forks, and because forks ship with workflows disabled, you enable them by hand before anything can trigger.
1
Go to your course clone ~/mustry-academy/cicd-for-ignition/: every lab is a folder under labs/; this one is labs/04-ignition-file-based-deploy. On WSL2, clone into your Linux home (~/…), never /mnt/c/…: the gateways' bind mounts are far slower and line endings get messy across the Windows boundary.
2
Fork & clone, once for the whole course. Already did it for an earlier lab? Skip this. Otherwise gh repo fork … --clone forks the course repo to your account and clones your fork in one go. Prefer the website? Press Fork on github.com, then git clone your fork.
3
Enable Actions. Open your fork's Actions tab and click "I understand my workflows, go ahead and enable them" (once per fork; the root course-setup.sh may already have done it). Skip this and nothing ever deploys. Then Settings → Actions → General → Approval for running fork pull request workflows from contributors → Require approval for all external contributors → Save: your fork is public and the runner holds the Docker socket, so no stranger's PR may start a job without your click (Lab 03's rule).
4
Create a runner PAT: the bundled runner needs it to register. At github.com/settings/tokens: Generate new token (classic) → tick the repo scope → Generate → copy the ghp_… value. You make this once; Lab 06 reuses the same token, so keep it handy.
5
Copy the env file with [ -f .env ] || cp .env.example .env (the root course-setup.sh may already have created it) and check two lines: point RUNNER_REPO_URL at your fork (not the course repo), and paste your token into RUNNER_GITHUB_PAT. Leave everything else as shipped: the admin logins stay as-is, and the three IGNITION_API_KEY_* lines stay empty: setup.sh generates a unique key per gateway into .env in the next step. No key ever lives in the repo.
6
Check the remotes and set the default: git remote -v (origin must show your username), then gh repo set-default <you>/cicd-for-ignition so gh targets your fork, not the course repo (once per clone; already done if you set it in an earlier lab). Then code . to open VS Code, and scripts/setup.sh brings up the stack (three gateways + TimescaleDB + the runner).

PART 1 · WE DO
Tour data/, catch a UI change on disk, read config as files
Three guided blocks from exercises/lab.md, then three changes solo. local bind-mounts ./services/config/, so whatever the gateway writes there also shows up in git status.
1
Tour. ls -la the gateway's data/ from inside the container and put every top-level entry in a bucket: project, gateway or operational.
2
Find the file. Touch /tmp/marker, change the Welcome Screen Notes in Platform → Gateway Settings, then find -newer the file it wrote. Note the scope in its path.
3
Again with a DB connection. Re-touch the marker, create a Postgres connection named Scratch (Connect URL jdbc:postgresql://timescaledb:5432/ignition_local_development, user ignition, Password → Embedded, ignition), find -newer, then git status. Which deployment-mode collection did it land in, and why does that matter for test vs production?
4
Everything is a file. Open the shipped TimescaleDB connection, the Simulator device and the example-tags tag definitions, diff the local-development vs production connection, and find where Perspective keeps its styles.
5
Go solo: make three changes from the list in lab.md (a view, a device, a user, a tag provider, a module). For each note: what you changed · where it lives on disk (relative to data/) · which bucket · would you commit it, one sentence why. Marker trick every time.
# 1: the tour
docker exec -it lab04-ignition-local bash -lc \
  "ls -la /usr/local/bin/ignition/data"

# 2-3: set a marker, click in the UI, find what changed
docker exec lab04-ignition-local touch /tmp/marker
#    ... make the change in the gateway UI ...
docker exec lab04-ignition-local find \
  /usr/local/bin/ignition/data/config -newer /tmp/marker -type f
git status                 # the same files, in your repo

# 4: deployment modes, one per-mode override
diff services/config/resources/{local-development,production}/ignition/database-connection/TimescaleDB/config.json
Heads-up

A UI edit lands in the collection selected in the Deployment Modes bar: local-development on local. Shared config belongs in core. And not everything on the host shows in git: a new user is written to …/user-source/default/users.json, which .gitignore hides because it holds password hashes.

PART 2 · WE DO
The deploy, by hand, once
Everything lab04-deploy.yml automates, done manually so the workflow holds no mysteries.
1
Edit a view that already exists: in the shipped overview view's view.json in example-project, change the label text "Run Control" to "Run Control v2". Local bind-mounts ./projects/, so editing the file in your working tree is editing the local gateway's disk.
2
Run scripts/scan.sh, then open localhost:8088/data/perspective/client/example-project: the top-left card reads RUN CONTROL V2. The scan makes the gateway notice what's on disk.
3
Ship to test by hand: docker cp the project, scan. Test starts empty, so nothing to wipe. Verify at localhost:8089/data/perspective/client/example-project: same view, same title. Every value shows a red null: test has no tags or connections yet, because you only copied the project. The first real deploy ships the config too. Bonus check from the host: ls gateways/test/projects shows what just landed.
4
Open .deployignore. For each pattern, say why the gateway shouldn't have that file. Notice the leading /: it anchors a pattern to the lab root, as in .gitignore. Without it, tests/ would also prune example-project's script package called tests.
# 1: edit the shipped view; the bind mount means your
#   working-tree edit is already on local's disk
#   projects/example-project/com.inductiveautomation
#     .perspective/views/pages/overview/view.json
#   "text": "Run Control" → "Run Control v2"

# 2 (local): just scan, then verify at :8088
scripts/scan.sh

# 3 (test): copy the project over, then scan the test gateway
docker cp ./projects/. \
  lab04-ignition-test:/usr/local/bin/ignition/data/projects/
scripts/scan.sh test
What lab04-deploy.yml adds

Before copying, it also wipes projects/ + config/ (sparing what .deployignore protects: config/local/, config/resources/local/, and the internal identity by name: user-source/default/ + user-source/opcua-module/ + identity-provider/default/, plus the gateway's own api-token/), so a resource deleted in the repo disappears from the gateway too. Other identity resources and security-properties are ordinary config and ship normally. You'll read that step in the workflow anatomy.

PARTS 2.1-2.2
Runner online + GitHub environments & secrets
15 min. The plumbing between your fork and your gateways. Steps 1, 3 and 4 happen on github.com, in your fork's Settings; the API key values come from your .env (setup.sh generated them).
1
Verify the runner (it's part of the compose stack). Then check your fork: Settings → Actions → Runners must show it online with labels self-hosted, lab04.
2
Not there? Three checks: RUNNER_REPO_URL points at your fork · RUNNER_GITHUB_PAT is a real repo-scope PAT, not the placeholder (a bad one shows a 401 in docker compose logs github-runner) · docker compose up -d --force-recreate github-runner.
3
Create environment lab04-gateway-test in your fork on GitHub (Settings → Environments → New environment) with secret IGNITION_API_KEY = the IGNITION_API_KEY_TEST value from your .env: the test gateway's own key (:8089).
4
Repeat on GitHub: environment lab04-gateway-production with IGNITION_API_KEY_PRODUCTION from .env: the production gateway's key (:8090). Other GitHub environment parameters (IGNITION_URL / IGNITION_CONTAINER) can be left as is.
# part 2.1: is the runner alive?
docker compose ps github-runner
docker compose logs --tail 50 github-runner
# look for "Listening for Jobs"
Per-gateway keys

API keys are per-gateway, not per-URL. The test key won't authenticate against production. And the runner reaches gateways by compose service name (http://ignition-test:8088). The host ports 8089/8090 are only how you reach the UIs.

PART 2.3
Ship to the test environment via the main branch
15 min. A real PR rides the pipeline: feature branch → PR → CI → merge → lab04-deploy.yml → test gateway.
1
Create a new project named sample-project on the local gateway, the way you always do in Ignition (Designer → New Project, or Platform → Projects). The bind mount drops it into your working tree: git status shows an untracked projects/sample-project/. That folder is your deployable.
2
Create one simple view in that project in the Designer (any name, e.g. a label with your name on it). Tick Page URL (/) in the New View dialog so a browser can open it. Save. That gives you something visible to recognize on the test gateway after the deploy.
3
Branch feature/add-sample-project off main, git add projects/ and commit (this also picks up the we-do's Run Control v2 edit, so the repo matches your local gateway), then push.
4
Open a PR into main on GitHub, base repository <you>/cicd-for-ignition (your fork, not the course repo). Watch lab04-ci.yml run on ubuntu-latest (free): yamllint, actionlint, shellcheck, ign-lint, docker compose config, JSON validity, .deployignore syntax, and the security-properties identity check.
5
Merge. lab04-deploy.yml fires (note the paths: filter, since docs-only pushes don't deploy). Validation already happened on the PR, so it goes straight to shipping. Watch the Ship and Trigger gateway scan steps. The first deploy to a fresh gateway restarts it once (Ignition picks its deployment mode at boot); every later deploy scans hot.
6
Verify at localhost:8089. Platform → Projects lists sample-project; its view opens at …/data/perspective/client/sample-project, and RUN CONTROL V2 now shows live values. From the host, ls gateways/test/projects shows the tree CI shipped: example-project, packaging-site and yours: the unit of deploy is the whole projects/ tree.
# 1-2: create project + view in Ignition, then look at the repo
git status              # untracked: projects/sample-project/

# 3: the feature branch
git switch main
git switch -c feature/add-sample-project
git add projects/
git commit -m "Add sample-project"
git push -u origin feature/add-sample-project
# then on GitHub: PR into main → CI green → merge

# 6: after the deploy, see what CI shipped
ls gateways/test/projects
Nothing deployed?

Two classic causes: the change didn't touch a deploy path (the paths: filter skipped it), or Actions isn't enabled on your fork.

PART 2.4
Release to production: main + a tag
10 min. The GitHub Flow release: tag the commit on main you want in production. The tag, not the merge, is what ships production.
1
The change is already on main from the test deploy, now tag it.
2
Observe: the tag is what ships production. The merge already shipped test, but only a lab04-v* tag reaches production.
3
Tag lab04-v0.1.0 and push the tag. lab04-release.yml fires: same five steps, different environment, production container. Tag already exists in your fork (inherited at fork time)? Take the next free number, git tag -l shows what's taken.
4
Verify at localhost:8090 (or Designer). Production now shows the change you merged into main and just released. Host-side check: ls gateways/production/projects.
# on main, the change is already there from the test deploy
git switch main && git pull

git tag lab04-v0.1.0
git push origin lab04-v0.1.0        # ← lab04-release.yml fires
Why tags

Production always runs a named, re-deployable version. That's also your rollback button: lab04-release.yml's workflow_dispatch takes a tag input, so re-deploying lab04-v0.1.0 is two clicks, no git surgery.

PART 2.5
Break a deploy on purpose
~5 min, optional but strongly encouraged, because reading the failure is half the lesson. Pick one.
A
Wrong API key. Set garbage in lab04-gateway-test's secret, re-run the deploy. The Ship step succeeds (docker cp doesn't care about keys), then the scan step gets a 401 and fails fast, naming the secret to check. The new files are on the gateway's disk, but no scan told it to load them: it keeps running the old state and you can still log in. What's your recovery story?
B
Stopped container. docker compose stop ignition-test, then trigger a deploy. The verify step fails fast: "container is in state 'exited', expected 'running'", before any file moved. Much better than failing halfway.
C
Then fix it and re-run the workflow (manual workflow_dispatch works too). The steps are idempotent, so the deploy converges.
# failure B: stop the target, watch verify fail fast
docker compose stop ignition-test
# … re-run lab04-deploy.yml from the Actions tab …
docker compose up -d ignition-test  # recovery
Write it down

For your chosen failure: symptom → state of the gateway → recovery → which workflow step should have caught it earlier? Bring the answer to the debrief.
