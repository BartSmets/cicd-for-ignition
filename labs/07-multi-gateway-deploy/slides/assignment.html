The assignment · ground rules
READ FIRST
How this works: you are contributors on a real, protected repo
  • We're here to get reps in. Everything from the past four days, on repeat: feature branch, commits, PR, review, tag, release pin, deploy. exercises/lab.md is the source of truth; these slides mirror it. Share your screen in the breakout room.
  • No fork this time. Everyone works in Mustry-Solutions/demo-oatmakers, the public repo behind Mustry's live Oatmakers demo. We add you as a collaborator; accept the invite and push your branches straight to that repo.
  • main is protected. Nothing reaches it without a pull request, a green CI OK check and one approval from someone else. You cannot approve your own PR: we do, or a fellow student does.
  • Two deploy channels, two triggers. Every merge to main lands on your own test gateway (you set that up in Part 0). Only a change to release.yaml on main reaches production: workflow Deploy, on the runner [self-hosted, demo-oatmakers]. Started by hand from another branch, it refuses.
  • Production is live and public: https://cloud.mustrysolutions.com. Customers see it, so be gentle. You verify through the public pages and the workflow logs; you do not need the admin login. Need a gateway status page? Ask, and we share access in the chat.
  • Stuck on the setup? The Troubleshooting section of exercises/lab.md covers the runner, the trial and stray file churn.
Ask early

Stuck for more than a couple of minutes? Say so in the room. Don't sit blocked in silence; that's exactly what we're here for.

The assignment · the mental model
MODEL
One repository, two jobs: the projects and the release file live together
Keep this picture in your head for the whole hour. Every move you make is on one side of it, and the seam between the two sides is a version string.
projects/ + the gateway payload
"What have we built?"
  • A tag like <yourname>@v1.0.0 marks a version of one project: a point in history you can deploy.
  • Nothing gets compiled: the deploy ships the files as they were at that tag.
  • A tag that was never pushed is a release that does not exist.
release.yaml
"What runs on production, right now?"
  • One file, one production gateway: oatmakers-site-7.
  • You change a version number by PR, and a deploy happens.
  • No workflow deploys any other way, and a pin may only point at a tag on a commit on main: only reviewed code ships.
# release.yaml
gateway: oatmakers-site-7
projects:
  oatmakers: v5.0.0   # + the gateway payload
One repo, by choice

In the teaching you saw option B: split the infra part (release files, gateway config) into its own repo, owned by another team. Both are valid. One repo keeps this lab small.

The assignment · etiquette
RULES
Rules for a shared live demo: how the whole group ships through one release file
Everyone in the group, and the Mustry team, deploys through the same release.yaml to the same gateway. These rules keep that civil.
1
Small PRs. One view, one migration pair, one module.
2
Stage only what you changed. git add <your paths>, never git commit -am: the gateway rewrites files on its own.
3
One release PR in flight at a time. Check the open PRs, say in the chat when you start, wait for Deploy to go green.
4
A conflict in release.yaml is normal: rebase and keep every pin (commands on the right).
5
Never lower a pin. Check whether your tag is already inside a higher one (Part 2).
6
A pushed tag is permanent. Made a mistake? Fix it on main and cut the next number.
7
Announce restarts. A module or a JAR restarts the production gateway.
8
Leave the existing demo alone. Your screens, tags and tables carry your name or Course.
git fetch origin
git rebase origin/main
# fix release.yaml: keep every pin
# from main, re-apply only your line
git add release.yaml
git rebase --continue
git push --force-with-lease
Rollback

Production looks wrong after a release? Say so in the chat straight away. The fix is the Revert button on the merged release PR, then review and merge as usual.

0A
Start your test gateway and register your runner with the shared token
Do this once, at the start, then leave it running all afternoon. It reuses a self-hosted runner (labs 03-06) and the push-to-main deploy you know from labs 04-06.
1
Tell the stack who you are. We post one runner registration token in the Zoom chat at the start of Part 0. Copy .env.example to .env, set LAB_USER (lowercase, no spaces) and RUNNER_TOKEN. Leave IGNITION_API_KEY empty.
2
Start the stack: ./scripts/setup.sh. It starts the local stack and, because LAB_USER is set, the test profile: your test gateway on 8090 and your runner. It also generates your API key and seeds it into the test gateway before its first boot, so always use setup.sh for the first start.
3
Check your runner is online. Contributors cannot open Settings → Actions → Runners, so read the runner's own log: Listening for Jobs means it is registered and waiting.
cp .env.example .env
# LAB_USER=<yourname>
# RUNNER_TOKEN=<the token from the Zoom chat>
./scripts/setup.sh

docker logs oatmakers-test-runner-<yourname> 2>&1 \
  | grep -E "Connected to GitHub|Listening for Jobs"
The token

One token for everyone, valid one hour. It can only enroll runners on this repo (it is not a login, so the chat is fine). Registering a runner is a repo-admin act, which is why it comes from us. Your runner trades it for its own credentials on the first start and keeps them in a volume. Missed the window? Say so: a fresh one takes five seconds.

Observe

Your runner is oatmakers-test-<yourname> with the labels self-hosted,<yourname>-local. Only jobs asking for that label run on your machine.

Part 0 · your test gateway · B
0B
Copy the workflow template under your name, merge it, and watch it deploy main to localhost:8090
The deploy workflow is already written. You copy it, put your name in it, and PR it in like anything else. Your own merge is the first push it deploys.
4
Make the provided workflow yours: copy test-example.yml.template to test-<yourname>.yml and replace CHANGEME with your name in the one line marked CHANGEME: runs-on.
5
PR it in: branch, git add that one file, push, open the PR, wait for CI OK, ask for an approval, merge.
6
Verify it works. Your merge is a push to main, so it starts your workflow: Actions → .github/workflows/test-<yourname>.yml runs on your runner and goes green, and localhost:8090/data/perspective/client/oatmakers/ serves the shared project. From now on every merge anyone makes runs it.
7
Test a branch before you merge it: gh workflow run test-<yourname>.yml --ref <your-branch> puts that branch on your test gateway. The next push to main puts main back.
git switch -c feature/<yourname>-test-workflow
cp .github/workflows/test-example.yml.template \
   .github/workflows/test-<yourname>.yml
# the one CHANGEME line: CHANGEME → <yourname>
runs-on: [self-hosted, <yourname>-local]

git add .github/workflows/test-<yourname>.yml
git commit -m "ci: add test deploy workflow for <yourname>"
git push -u origin feature/<yourname>-test-workflow
Observe

The runner label is the whole routing story. Everyone has a push-to-main workflow, and each deploys only to its owner's test gateway. The label is written out per file because GitHub resolves runs-on before any per-user context exists. Production works the same way: [self-hosted, demo-oatmakers].

Part 1 · your project · B
1B
Tag your release, pin it in release.yaml, and watch Deploy bring it live
Two moves: make the release exist, then point production at it. In that order: CI refuses a pin whose tag does not exist.
5
Tag the merged main: <yourname>@v1.0.0, and push the tag. Never tag your feature branch: a tag must point at a commit on main. The tag is the release; the deploy copies the files as they were at that tag.
6
Pin it: check the open PRs (one release PR in flight at a time), branch, add one line to release.yaml, stage only that file, push, PR, CI OK, approval, merge. Conflict with someone else's pin? Rebase and keep both lines.
7
Watch it go live: Actions → Deploy on the demo-oatmakers runner. When it is green, open cloud.mustrysolutions.com/data/perspective/client/<yourname>/.
git switch main && git pull
git tag <yourname>@v1.0.0
git push origin <yourname>@v1.0.0

git switch -c pin/<yourname>-v1.0.0
# release.yaml
 projects:
   oatmakers:  v5.0.0
+  <yourname>: v1.0.0
git add release.yaml
git commit -m "release: pin <yourname> v1.0.0"
git push -u origin pin/<yourname>-v1.0.0
Observe

CI checks that <yourname>@v1.0.0 exists and sits on main before it lets the pin through, so the tag comes first. Pushed it after opening the PR? A tag push does not re-run CI: Checks → Re-run failed jobs (or gh run rerun <id> --failed).

✅ Part 1 gate

Your project merged through an approved PR, the tag <yourname>@v1.0.0 pushed, your line in release.yaml merged through an approved PR, your view live on production. You just did the full loop.

4
Finished means live: merge, cut the next free oatmakers@ tag (from v5.0.0: a fix v5.0.1, a feature v5.1.0), pin it by PR. The gateway payload rides the oatmakers pin.
git switch main && git pull
git fetch --tags
git tag -l 'oatmakers@*' --sort=-v:refname | head -3
git tag oatmakers@v5.1.0          # the next free number
git push origin oatmakers@v5.1.0
# rejected? someone took it: drop yours, take the next
git tag -d oatmakers@v5.1.0 && git fetch --tags
# release.yaml already pins a HIGHER oatmakers@ version?
# check whether your tag is inside it before you pin:
git merge-base --is-ancestor \
  oatmakers@v5.1.0 oatmakers@v5.2.0 && echo "already included"
Observe

Already included means your change ships with the higher pin: you are done, never pin backwards. No output: cut a new tag from the current main and pin that.

CHALLENGE 3 · DATABASE
  • A connection named Course_<yourname> to jdbc:postgresql://postgres:5432/ignition (resolves locally and on production). Username: the plain string ignition. Password: the referenced secret POSTGRES_PASSWORD from the file secret provider named environment. You never see the value.

Careful

Your test workflow migrates this same local database: leave it migrated on a branch and every test run on main fails with no migration found for version N. Pick a number higher than any on main at merge time: a lower number merged after a higher one ran is silently skipped. Same number as someone else after a rebase? Renumber yours.

SymptomFix
"Waiting for a runner to pick up this job" on your test-<yourname> runThe runs-on label does not match your runner. It must be exactly <yourname>-local, the same name as LAB_USER. Check docker logs oatmakers-test-runner-<yourname> for Listening for Jobs.
The runner log says the token is invalid or expiredAsk for a fresh token in the chat, put it in .env as RUNNER_TOKEN, re-run ./scripts/setup.sh.
Blank Perspective pages, Designer disconnects, a deploy that worked failsThe trial lapsed: scripts/reset-trial.sh.
git status shows files you never touchedGateway churn (module fingerprints, resource.json stamps), not your change: do not stage it. See docs/resource-json-hygiene.html. Except store-and-forward-engine/<name>/ and tag-definition/System/Gateway/{Devices,Database,StoreAndForward}/<name>/ for a device, connection or historian you added: stage those with it.
Test run fails: no migration found for version NYour local database ran a migration from a branch main does not have. On that branch: scripts/migrate.sh down 1, then re-run.
Test run says Still not authorizedYour test gateway holds an older API token than your .env. docker compose --profile test rm -sf test-gateway test-runner && docker volume rm oatmakers_test-gateway-data && ./scripts/setup.sh, then re-run.
CI OK is red on a release PROpen the failing job. Most often the pin points at a tag that was never pushed (git push origin <tag>) or not on main, or the YAML lost a line in a rebase. After pushing a tag: Checks → Re-run failed jobs (gh run rerun <id> --failed).
